# Idea Discovery

既存の発想の延長では届きにくいアイデアを求められた時に、よくある失敗を避けるためのSkillである。発見を保証する方法ではない。ここに書く進め方は、長い探究の中で残った仮説であり、効果はまだ検証されていない。

## 使わない場面

次の場合はこのSkillを使わず、通常どおり答える。

- 既存の選択肢から選べばよい設計判断（`engineering-decisions`）
- 実装前に要件を整理する作業（`design-refinement`）
- 案を幅広く列挙してほしいという依頼
- 事実や実験で答えが決まる問い

## 防ぐ失敗

1. **成功例から方法を抜き出す。** 優れた発明の共通点（前提を疑う、機能を取り除く、問題を定義し直す等）を手順にしても、それは後付けの説明である。同じ手順で失敗した事例は見えていない。成功を説明できることと、成功を再現できることは別である。
2. **候補を大量に出し、今の基準で順位をつける。** 根本的に新しい考えほど、今の評価基準では価値が見えない。早い段階で絞ると、それを捨ててしまう。
3. **考え込むうちに思い込む。** 一つの候補を繰り返し考察すると、根拠のないものでも重要に見えてくる。後付けの正当化は、発見とよく似て見える。
4. **手法そのものに期待する。** 思考を分岐させる、独立に複数回試す、といった操作は、それ自体が発見を生むわけではない。どの文脈を引き継がせ、何を引き継がせないかという条件の一つにすぎない。

## 進め方

1. **一つの具体的な考えを成立させる。** 最も有望な答えを探す必要はない。使ってみられる程度に具体的な考えを、一つだけ立てる。
2. **良否を判定せずに使う。** その考えが正しいか、有用かを判定する代わりに、実際に当てはめて使ってみる。使うことで初めて出てくる問いを一つ立てる。
3. **その問いから成果を一つ作る。** 最初の問いに直接答えるだけでは出てこなかった、具体的な成果を一つ作る。設計の案、試作、比較できる実験、問題の新しい定式化などである。
4. **何も生まれなければ、そう言う。** 成果が出なければ、元の問いにそのまま答え、出なかったことを伝える。無理に意味を見いだしてはいけない。

画面・図版・映像のような視覚的・時間的な成果物では、2の「使う」は実際に作って見ることである。価値を言葉だけで判定すると、新しい考えほど既存の評価基準で捨てられやすい。下書き、一枚の画像、短い再生など、最も安い形で実物にし、見て気付いたことから問いを立てる。良否は agent が判定せず、直接答えた場合の成果物と並べて user に示す。

既定では1回だけ回す。user が続けるように求めた場合だけ、できた成果を次の「一つの考え」として繰り返す。

前の考察を引き継がずに試したい場合は、fresh context の subagent に元の問いだけを渡して、同じ進め方をさせてよい。ただし、それで良くなると決めつけない。

## 発見か、後付けかを確かめる

成果を出したら、user へ返す前に次を確かめる。

- **具体的で、確かめられるか。** 作れる、動かせる、比べられる、反証できる形になっているか。言い換えや抽象的な示唆だけなら、それは成果ではない。
- **直接答えた場合と違うか。** 最初の問いに直接答えたらどうなるかを先に短く書いておき、成果と比べる。直接の答えの言い換えにすぎないなら、そう伝える。
- **進め方の意図に照らして採点していないか。** 「手順どおりに問いと成果が出たか」で良否を決めない。出力が手順に沿っていることと、優れた発見であることは別である。

## 伝え方

成果は仮説として伝える。発見だと言い切らない。次の3点を短く添える。

- 何をして、何が出てきたか
- 直接答えた場合と何が違うか
- 何を確かめれば正しいか、または違うかが分かるか
